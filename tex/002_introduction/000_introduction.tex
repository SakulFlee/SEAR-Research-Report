\labeledsection{Introduction}
The term \textit{Dependency-Injection} was formulated by~\textcite{dependency_injection_pattern}.
\textit{Dependency-Injection} is an addition to the \textit{concept of inversion of control}.\\
The \textit{concept of inversion of control} describes the process of inverting the flow of control within a system, compared to the traditional control flow. 
By doing this, the modularity and extendability increases~\parencite{designing_reusable_classes, object_oriented_framworks}.

In \textit{Dependency-Injection}, the process of obtaining dependencies is inverted.
Instead of linking dependencies with or into the application, the application itself searches for dependencies and loads them dynamically.
Doing so not only makes applications much more extendible but gives the option to have optional dependencies~\parencite{dependency_injection_pattern, empirical_study_dependency_injection, effects_of_dependency_injection_on_maintainability, enterprise_application_development_using_dependency_injection}.

When referring to \textit{injecting dependencies} we either, mean overwriting a required \textit{dependency} and thus changing its behaviour, or, adding and loading a new previously not needed (i.e.~optional) \textit{dependency} to extend the application.

For better understanding, we consider the following examples:\\
An application may have a part that is responsible for talking and exchanging information to and from a specific database server.
There can be two versions of this: A production-ready and a development-environment piece.
Instead of creating two separate applications (e.g. one for production, one for development), the application can use some internal logic (e.g.~direct input, configuration files or environment flags) to determine which version to use (i.e.~inject).
The same application may have another feature that lets it cache those requests.
However, this is not always wanted. 
Thus it is optional and can be enabled by adding and loading a dependency dynamically (i.e.~injecting it).

Another real-life example of optional dependencies is \texttt{Visual Studio Code}.
\texttt{Visual Studio Code} has a defined \textit{Extension API}~\parencite{visual_studio_code}.
Each extension builds upon this API and is in itself independent and optional.
However, a user can now dynamically install (i.e.~inject), remove, enable or disable an extension, without the need of recompiling the application.

The main security risk, which we are also focusing on in this report, comes from the fact that external \textit{dependencies} may not always come from the same developers.
Thus, the application creators cannot guarantee the trustworthiness and safety of these dependencies.
Usually, there are measures taken to prevent unsafe extensions, but there also is usually a way to turn those measures off or add an exception for specific extensions.
Thus, ultimately, the user is a high-risk factor and should always be warned.
Additionally, it is incredibly easy to hide malicious code this way and overwriting trusted dependencies will probably not even be noticed.

The following positive benefits and contrary negative impacts can be observed:
\begin{center}
    \begin{tabular}{|p{0.45\textwidth}|p{0.45\textwidth}|}
        \hline
        \textbf{Positive benefits} & \textbf{Negative impacts} \\\hline
        \begin{itemize}
            \item Application easy to extend
            \item Separation of code bases into dependencies
            \item Design decision to implement \textit{dependency-injection}
            \item Optional dependencies
            \item Configurability\footnotemark[1]
        \end{itemize} &
        \begin{itemize}
            \item Easy to exploit
            \item Third-party dependencies cannot be trusted
            \item Hard to shield against
            \item True security almost impossible to archive
            \item Difficult to find malicious code hiding in genuine applications
        \end{itemize}
        \\\hline
    \end{tabular}
    \captionof{table}{Positive benefits vs. Negative impacts}
\end{center}
\footnotetext[1]{User can decide what to install}
