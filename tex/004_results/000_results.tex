\labeledsection{Results}
The previous section did introduce our methods and defined the experiment.
This section will address our findings and give a transition to the following discussion part.

With the experiment defined, we can perceive how such a simple plugin system can be a considerable threat to the whole operating environment.
Especially with unprotected systems, a plugin can do virtually anything.
With the assumption that \textbf{all} plugins (extensions, modules, dependencies, libraries, \dots) are developed by the same application developers and are tested, there should be nearly no direct risk.
However, as soon as a (or multiple) third-party developers get introduced, the potential risk rises dramatically.
Not only are third-party plugins posing a high threat, but hijacking\footnote{introducing malicious code} such can be even more straightforward than official plugins.
Additionally, enabling third-party plugins probably also enables the manual installation of plugins, which in itself can be a high risk already.
Instead of getting plugins from a controlled central location, they now can come from anywhere and be possibly impossible to check for genuineness.

It should be clear that by utilizing  \textit{dependency-injection} the application can pose a threat to the whole environment by the simple fact that the original application developers do not have control over what these plugins may or may not do.
With the current plugin system, a plugin can do everything the operating user could do.
Depending on their system permissions, the damage could be minimal but could also be tremendous.
However, not everything is terrible.

With \textit{dependency-injection}, an application becomes much more extendable and flexible.
Depending on the plugin API, a plugin can potentially change the whole application in a way not even anticipated by the application developers.
Opening up the plugin development to third-parties can build a great and big community, potentially extending the application with zero-cost.
On top of that, each user can individually choose which components are needed and thus creating an individual configured application for themselves.

To further demonstrate possible exploits, we describe two possible scenarios:\\
In the first exploit, a module got replaced with a hijacked one.
The hijacked module does not do anything other than the original module but returns wrong results.
This exploit could, for example, lead to a disaster in the accounting department.
\clearpage
The second exploit tries to do as much damage as possible.
By utilizing access to the system, it tries to delete data and thus will ultimately render the current system useless.
Such an exploit could delete essential data and possibly even ruin a whole environment.

It is easier to shield against the second exploit as this one requires shell/system access (such as BaSH on Linux) and sufficient user rights to perform destructive tasks.
However, shielding against the first exploit is very difficult as the hijacked module most likely seems like the original one.

Ultimately, it should be clear that when implementing \textit{dependency-injection}, the overall security and safety of all users, systems and environments are at risk. 
Thus security measures must be considered.
